# 단디 Issue에서 PR까지

저장소의 `Issue → 브랜치 → 구현 → 검증 → PR` 작업 흐름을 따른다.
저장소 정책은 적용 범위의 `AGENTS.md`를 기준으로 하고, 반복 실행 절차에는 이 Skill을
사용한다.

## 작업공간 확인

- 루트 `AGENTS.md`와 변경 파일에 적용되는 모든 하위 `AGENTS.md`를 읽는다.
- 현재 브랜치, 작업 트리 상태, 관련 기준 문서를 확인한다.
- 사용자의 관련 없는 변경을 보존하고, 임의로 이동·커밋·덮어쓰기하지 않는다.
- 이슈, 사용자 요청, 저장소 맥락에서 기준 브랜치를 결정한다. 다른 통합 브랜치를 사용하는
  저장소에서 `main`을 임의로 가정하지 않는다.

## 이슈 생성 또는 재사용

- 전달받은 이슈가 있으면 재사용한다.
- 이슈가 없으면 작업을 `feat`, `fix`, `docs`, `refactor`, `test`, `chore` 중 하나로 분류한다.
- 이슈 제목을 `<type>: <작업명>`으로 작성한다. 예: `feat: 수정 계약서 대조 결과 표시`.
- `.github/ISSUE_TEMPLATE/`에서 가장 가까운 양식을 사용한다.
- 문제, 포함·제외 범위, 관찰 가능한 완료 조건, 영향 영역, API·데이터·상태 영향을 작성한다.
- 계약 전문, 개인정보, API 키, 서명 링크, 비밀정보를 이슈에 포함하지 않는다.
- GitHub 이슈 생성·수정을 외부 작업으로 취급하고 사용자가 요청한 경우에만 실행한다.

## 연결 브랜치 생성

- 작업 브랜치를 만들기 전에 이슈 번호를 확보한다.
- 브랜치 유형을 이슈 제목의 유형과 일치시킨다.
- 브랜치 이름을 `<type>/#<issue-number>/<작업명>`으로 작성한다.
- 작업명 부분의 앞뒤 공백을 제거하고, 공백을 하이픈으로 바꾸고, Git ref에 허용되지 않는
  문자를 제거하고, 반복 구분자를 피하고, 간결하게 유지한다.
- 간결한 한글 또는 영문 소문자 이름을 사용한다. 예: `feat/#123/수정-계약서-검증`.
- 관련 없는 미커밋 변경이 의도치 않게 따라갈 때는 브랜치를 전환하지 않는다.

## 변경 범위 파악 및 구현

- [references/change-impact.md](references/change-impact.md)를 읽는다.
- 영향받는 P0 생애주기 단계와 가장 작은 완결된 수직 범위를 식별한다.
- 공개 응답이나 영속 상태를 바꾸기 전에 스키마와 API·데이터 문서를 먼저 갱신한다.
- migration을 추가 전용으로 유지한다.
- 추출·검토 항목의 `source_page`, `source_text`, `confidence`를 보존한다.
- 날짜, 금액, 비율, 상태 전이를 결정적 코드로 구현한다.
- 외부 호출을 명시적인 `mock`·`live` Adapter 뒤에 둔다. 명시적 승인과 검증된 설정 없이는
  live 모드를 사용하지 않는다.
- 요청 자동 발송, 역제안 자동 수락, 서명 자동 시작, 증빙 자동 승인, 계약 자동 갱신을 하지 않는다.
- 모든 구현 변경에 테스트를 추가하거나 갱신한다.

## 작업 검증

- [references/change-impact.md](references/change-impact.md)에 따라 대상 검사를 먼저 실행하고,
  영향 범위에 필요한 상위 검사를 이어서 실행한다.
- 현재 환경에서 성공적으로 완료되지 않은 검사를 통과했다고 보고하지 않는다.
- diff에서 비밀정보, 계약 전문, 개인정보, 서명 링크, 관련 없는 변경, 광범위한 포맷 변경을 확인한다.

## 커밋 및 Pull Request 준비

- 커밋 제목을 `<type>: <요약>` 형식으로 작성하고 하나의 목적에 집중한다.
- 사용자가 요청한 경우에만 커밋, push, PR 생성처럼 저장소 이력이나 외부 상태를 바꾸는 작업을 한다.
- PR 제목을 `<type>: <작업명>`으로 작성한다.
- `.github/pull_request_template.md`를 사용하고 `Closes #<issue-number>`를 포함한다.
- 실제로 실행한 명령과 결과를 기록하고, 실행하지 않은 검사는 이유를 설명한다.
- API, 영속 상태, migration, 외부 Adapter, 개인정보, P0 경로 영향을 설명한다.
- 화면 변경이 있으면 스크린샷을 첨부하고, 없으면 해당 없음을 작성한다.
- 계약 전문, 개인정보, 비밀정보, 서명 링크를 PR에 포함하지 않는다.

## 작업 인계

- 생성하거나 재사용한 이슈 번호와 브랜치를 보고한다.
- 변경된 동작과 중요 파일을 요약한다.
- 검증 결과와 실행하지 않은 검사를 나열한다.
- 남은 위험, 결정 사항, 후속 작업을 알린다.
