# 단디계약

## 부산 관광상권 소상공인을 위한 AI 광고대행 계약 CLM

> 문서 목적
> 
> 
> 4인 팀이 일주일 안에 실제 배포·시연할 수 있는 범위로 확정한 최종 기획안
> 

---

## 0. 최종 결론

### 한 줄 소개

> 광고대행 계약에서 내가 이해한 조건과 실제 문서를 AI가 비교하고, 꺼내기 어려운 조정 요청을 대신 작성해 전자서명으로 확정하며, 산출물 확인과 재계약 시점까지 관리하는 소상공인용 CLM
> 

### 발표용 메시지

> 읽지 못한 계약을 읽어주고, 하지 못한 말을 대신해준다.
> 

### 개발 형태

- 반응형 웹서비스 (데스크톱용으로 개발)
- **소상공인**용 관리자 화면과 **대행사**용 무가입 응답 화면
- 하나의 대표 계약과 하나의 대표 산출물 흐름을 완성
- 네이티브 앱, 다국어 지원, 실제 송금, 광고 성과의 자체 측정은 개발하지 않음

### MVP 성공 기준

아래 흐름이 실제 배포 환경에서 한 번에 동작하면 MVP가 완료된 것이다.

`계약서 업로드 → 조건 추출 → 불일치·누락 검토 → 조정 요청 → 상대방 응답 → 변경·확인 합의서 → 모두싸인 → 산출물 증빙 → 만료·재계약 확인`

## 1. 문제 정의

부산 관광상권의 소상공인은 온라인 광고·SNS 홍보 제안을 자주 받지만, 계약을 전문적으로 검토하고 조건을 협상할 인력이 부족하다.

### 현재 계약 흐름

`대행사 전화·방문 영업 → 조건 설명 → 대행사 양식 계약서 전달 → 소상공인 서명`

소상공인은 다음 문제를 겪는다.

- 안내받고 이해한 기간·금액과 계약서가 다르다.
- 월 비용만 듣고 총 계약금액을 알지 못한다.
- 환불·성과보장을 들었지만 계약서에 근거가 없다.
- 산출물 수량·채널·보고 방식이 모호하거나 비어 있다.
- 중도해지 위약금과 자동갱신 조건을 놓친다.
- 불리한 조건을 발견해도 상대에게 어떻게 말할지 어렵다.
- 체결 후 무엇을 언제 받아야 하는지 다시 계약서를 찾아야 한다.

### 핵심 해결 질문

1. 내가 이해한 설명과 실제 계약조건은 같은가?
2. 총 얼마를, 얼마 동안, 무엇을 받기 위해 지급하는가?
3. 해지·환불·자동갱신·책임 조건은 명확한가?
4. 바꾸고 싶은 조건을 어떻게 정중하게 요청할 것인가?
5. 합의된 변경사항을 어떻게 다툼 없이 남길 것인가?
6. 체결 후 약속한 산출물과 재계약 시점을 어떻게 확인할 것인가?

### 제품의 공정한 포지션

단디계약은 소상공인에게 무조건 유리한 계약을 만들거나 대행사의 사기 여부를 판정하지 않는다.

> 양측이 같은 조건을 이해하고, 조정 과정과 최종 합의를 문서로 남기도록 돕는다.
> 

대행사도 자신이 수락·거절·역제안한 내용과 사유를 기록으로 남길 수 있어 사후 분쟁을 줄일 수 있다.

## 2. 핵심 사용자와 대표 시나리오

### 주 사용자

- 부산 관광상권의 음식점·카페
- 게스트하우스·소형 숙박업소
- 공방·체험업체
- 관광기념품 판매점

### 상대 계약자

- 온라인·SNS 광고대행사
- 블로그 마케팅 대행사
- 인플루언서·콘텐츠 제작자
- 관광상품 프로모션 운영사

### MVP 대표 계약

> 광안리 카페와 홍보대행사의 SNS·블로그 광고대행 및 매장 촬영 계약
> 

대표 업무:

- 블로그·SNS 콘텐츠 제작
- 매장 사진·영상 촬영
- 외국인 관광객 대상 홍보물 제작
- 월별 광고 집행 결과 보고

대표 확인 항목:

- 계약기간과 총액
- 해지·환불·자동갱신
- 콘텐츠 종류·수량·게시 주기
- 촬영 중 시설·장비 파손 책임
- 초상권·콘텐츠 소유권과 2차 사용
- 결과 보고와 증빙 의무

## 3. 모두싸인 CLM 단계 적용

| 단계 | 실제 구현 기능 | 핵심 산출물 |
| --- | --- | --- |
| 작성 | 계약서 업로드, 내가 이해한 조건 5문항 입력 | 계약 레코드 |
| 검토 | 조건 추출, 불일치·누락·빈칸·확인 신호 표시 | 근거가 연결된 조항 카드 |
| 조율 | 요청할 문구 선택, 링크 발송, 상대방의 1회 응답 | 구조화된 조정 이력 |
| 체결 | 변경·확인 합의서 생성, 모두싸인 양측 서명 | 전자서명 완료 문서 |
| 보관 | 원계약·분석·조율·체결 상태 타임라인 | 감사 가능한 계약 기록 |
| 관리 | 대표 산출물 제출·확인, 광고 리포트 기록·대조, 만료·해지통보기한 표시 | 이행 상태와 월별 광고효과 기록 |
| 분석 | 계약·위험·조율·이행·만료 현황 집계 | 최소 대시보드 |

`조율`은 별도의 일곱 번째 CLM 단계가 아니라 검토와 체결 사이의 제품 흐름으로 설명한다.

### 관리 단계의 현실적 범위

관리 기능은 전체 프로젝트 관리가 아니라 다음 두 흐름만 구현한다.

`산출물 1건 자동 생성 → 소상공인 체크리스트 직접 확인·선택적 URL 기록 → 지급 조건 충족 표시`

`대행사 리포트 업로드 → 지표 추출·확인 → 계약 조건 대조 → 문의 문안 생성` (6.14)

다음은 구현하지 않는다.

- 광고 게시물의 실제 존재 여부 자동 검증
- 광고 성과의 자체 측정과 매출 기여도 분석
- 실제 지급 승인 또는 송금 (보류)
- 다단계 검수·산출물 버전 관리

## 4. 과제 요구사항 매핑

| 과제 요구 | MVP 적용 |
| --- | --- |
| 약관·계약 파싱·구조화 | Upstage Document Parse로 구조 보존, Information Extract로 요금·기간·해지·환불·안전·책임·산출물 추출 |
| 리스크 점검·경고 | Solar가 불일치·누락·불명확·확인 필요 항목을 쉬운 말로 설명 |
| 표준 안전장치 제안 | 원안 수용·절충안·요청안 3종 문구 제안 |
| 다국어 지원 | MVP에서 제외하고 조율·전자서명·최소 이행 흐름의 완성도에 집중 |
| 전자서명·증빙 | 모두싸인 API로 요청·진행·완료·실패 상태 처리 및 체결본 ID 보관 |
| CLM 관리·분석 | 최소 이행 확인, 만료·자동갱신 표시, 계약 현황 대시보드 |

### 다국어 범위 결정

- 일주일 MVP에서는 다국어 요약·설명·UI를 구현하지 않는다.
- 과제 요구사항 중 미구현 항목으로 명확하게 공개한다.
- 발표에서는 핵심 계약 흐름을 안정적으로 완성하기 위한 범위 결정이라고 설명한다.
- 후속 버전에서는 구조화된 핵심조건을 대상으로 참고용 다국어 요약을 추가할 수 있다.

## 5. 전체 사용자 흐름

### 5.1 소상공인 흐름

1. 계약을 새로 등록한다.
2. 계약서 PDF를 업로드한다.
3. 내가 안내받고 이해한 조건 5문항에 답한다.
4. AI가 핵심조건과 확인 신호를 추출한다.
5. 원문 페이지를 보며 조항 카드를 검토한다.
6. 요청할 조항을 선택한다.
7. 조정 요청서를 미리 보고 상대방에게 링크를 보낸다.
8. 상대방의 수락·거절·역제안을 확인한다.
9. 역제안과 원 요청의 차이를 AI 설명으로 확인한다.
10. 변경·확인 합의서를 생성한다.
11. 모두싸인으로 양측 전자서명을 요청한다.
12. 서명 완료 상태와 계약 타임라인을 확인한다.
13. 대표 산출물 증빙을 확인하고 승인 또는 이의 제기한다.
14. 만료·자동갱신 시점에 유지·조건 변경·종료를 선택한다.

### 5.2 대행사 흐름

1. 이메일 또는 데모용 링크로 조정 요청서를 연다.
2. 별도 가입 없이 토큰으로 접근한다.
3. 조항별로 수락·거절·역제안 중 하나를 선택한다.
4. 거절·역제안 시 한 줄 사유를 입력한다.
5. 전체 응답을 제출한다.
6. 모두싸인 링크에서 서명한다.
7. 대표 산출물은 소상공인이 서비스의 이행 체크리스트에서 직접 확인한다.

### 5.3 사용자가 입력한 설명의 신뢰 수준

`구두 설명`이라는 표현 대신 `내가 안내받고 이해한 조건`을 사용한다.

| 입력 자료 | 서비스 표시 |
| --- | --- |
| 계약서 | 계약 문서상 조건 |
| 제안서·견적서·메시지 | 문서로 확인된 설명 |
| 녹취·전사본 | 기록된 설명 |
| 사용자의 5문항 답변 | 사용자가 기억하고 이해한 설명 |

사용자 답변만 있는 경우 “대행사가 다르게 말했다”라고 단정하지 않고 “내가 이해한 내용과 계약서가 다릅니다”라고 표시한다.

## 6. 핵심 기능 상세

### 6.1 계약 업로드와 조건 입력

필수 입력:

- 광고대행 계약서 PDF
- 이해한 계약기간
- 이해한 월 납부액
- 이해한 총 계약금액
- 이해한 환불조건
- 이해한 중도해지 가능 여부

선택 입력:

- 광고 제안서·견적서
- 담당자 메시지 캡처 또는 텍스트

### 6.2 문서 파싱과 구조화

추출 필드:

- 계약 당사자
- 계약 시작일·종료일
- 월 납부액·총 계약금액
- 선결제·할부
- 자동갱신·해지 통보기한
- 중도해지·위약금·환불
- 광고 채널
- 콘텐츠 종류·수량·게시 주기
- 결과 보고 주기
- 성과·환불보장 문구
- 광고계정·콘텐츠 소유권
- 촬영 안전·시설 파손·손해 책임
- 초상권·개인정보
- 허위·과장 광고 책임

각 결과에 다음을 저장한다.

```json
{
  "field": "contract_total_amount",
  "value": 6000000,
  "sourcePage": 2,
  "sourceText": "총 계약금액은 금 육백만원으로 한다.",
  "confidence": 0.96
}
```

총액·기간·위약금 계산은 코드로 수행하고 LLM 계산에 의존하지 않는다.

### 6.3 빈칸과 불명확 표현 검출

- 공란·미기재 필드
- 수기 입력 예정 칸
- “별도 협의”
- “추후 결정”
- “상황에 따라 변경”
- 수량·기한·책임 주체가 없는 표현

### 6.4 불일치와 확인 신호

MVP 탐지 범위:

- 계약기간 불일치
- 월 납부액·총액 불일치
- 환불 설명의 계약상 근거 없음
- 중도해지 가능 여부·위약금 불일치
- 자동갱신·해지통보기한
- 산출물 수량·보고 의무 누락
- 촬영 안전·손해 책임 누락 또는 일방 전가

허용 표현:

- 설명과 계약서가 다름
- 계약서에서 근거를 찾지 못함
- 조건이 명확하지 않음
- 추가 확인이 필요함
- 전문가 검토가 필요할 수 있음

금지 표현:

- 사기 업체
- 불법 계약 확정
- 안전한 업체
- 승소 가능성
- 법률 자문을 대체한다는 표현

### 6.5 조항 카드

카드 구성:

1. 계약서 원문과 페이지
2. 내가 이해한 조건
3. 무엇이 다른지 쉬운 설명
4. 공식 기준 또는 내부 검토 규칙
5. 선택 가능한 문구
    - 원안 수용
    - 절충안
    - 요청안
6. 모델 확신도와 한계

사용자는 문장을 처음부터 작성하지 않고 기본 문구를 선택한다.

### 6.6 톤 완충

자유 입력은 허용하지만 그대로 발송하지 않는다.

```
입력: 5년은 너무 길어요.
제안: 계약기간을 1년으로 조정하고, 상호 만족 시 연장하는 방식을 제안드립니다.
```

발송 전 원문·변환문을 함께 보여주고 사용자가 승인해야 한다.

### 6.7 조건 조정

MVP에서는 무한 협상이 아니라 한 번의 구조화된 응답만 지원한다.

`요청 생성 → 발송 → 열람 → 조항별 응답 → 합의·원안 유지 확정`

대행사 선택:

- 수락
- 거절 + 사유
- 역제안 + 문구 + 사유

역제안이 오면 AI가 다음을 한 번 설명한다.

- 원 요청에서 달라진 부분
- 유지된 위험 또는 확인 항목
- 소상공인이 최종 확인할 내용

자동 재요청과 반복 협상 Agent는 P2로 제외한다.

### 6.8 변경·확인 합의서

문서명:

> 광고대행 계약조건 변경·확인 합의서
> 

포함 항목:

- 원계약 명칭·체결일·문서 식별자
- 계약기간·총액·결제 일정
- 산출물·채널·보고 방식
- 해지·환불·자동갱신
- 콘텐츠 권리·촬영 안전·손해 책임
- 변경 전·변경 후 조건
- 거절·철회된 요청과 원안 유지 표시
- 변경되지 않은 조건의 처리 원칙
- 양측 서명란

조정 요청에는 사용자가 선택한 한 개 이상의 조항을 개수 상한 없이 모두 포함한다.

### 6.9 모두싸인 연동

실제 구현:

- API 인증
- 템플릿 조회
- 서명자 2명 지정
- 템플릿 데이터 입력
- 서명 요청
- 문서 상태 조회
- 웹훅 수신
- 완료·거절·실패 상태 저장
- 문서 ID와 완료 시각 저장

상태:

`ON_PROCESSING → ON_GOING → COMPLETED / ABORTED / PROCESSING_FAILED`

서비스 화면에서는 이를 `처리 중 → 서명 진행 중 → 서명 완료 / 중단 / 처리 실패`로 변환해 표시한다. 웹훅은 중복 수신될 수 있다는 전제로 문서 ID와 이벤트 ID를 이용해 중복 처리하지 않는다.

### 6.10 보관과 감사 타임라인

한 화면에서 다음 이벤트를 시간순으로 보여준다.

- 계약 업로드
- 사용자 조건 입력
- AI 분석 완료
- 조정 요청 발송
- 대행사 열람·응답
- 합의 확정
- 모두싸인 서명 요청·완료
- 산출물 제출·확인
- 만료·재계약 검토

MVP에서는 체결본 파일을 서비스가 직접 영구 보관하는 것보다 모두싸인 문서 ID·상태와 원본 계약 파일을 연결해 조회하는 데 집중한다.

### 6.11 최소 이행 관리

계약 분석 결과의 첫 번째 명확한 산출물을 이행 항목으로 자동 생성한다.

```json
{
  "title": "인스타그램 게시물 4건",
  "dueDate": "2026-08-20",
  "assignee": "AGENCY",
  "evidenceType": "URL",
  "status": "PENDING"
}
```

상태:

`PENDING → APPROVED / DISPUTED` 또는 기존 공개 제출 호환 흐름
`PENDING → SUBMITTED → APPROVED / DISPUTED`

기능:

- 소상공인의 계약 원문·기한 체크리스트 확인
- 소상공인의 선택적 증빙 URL 입력
- 소상공인의 확인 완료 또는 문제 있음 선택
- 기존 공개 제출 링크는 호환 경로로 유지하되 기본 화면에서 요청하지 않음
- 확인 완료 시 `지급 조건 충족` 표시
- 실제 송금·결제 API 없음

### 6.12 계약 일정과 재계약

계약서에서 추출한 날짜로 다음 상태를 계산한다.

- 계약 만료 D-30
- 해지 통보기한 D-14
- 자동갱신 임박 D-7

MVP는 외부 문자·카카오 알림 대신 웹 대시보드 알림을 구현한다.

사용자 선택:

- 동일 조건 재계약
- 조건 변경 후 재계약
- 종료

조건 변경을 선택하면 이전에 거절되거나 원안 유지된 조항을 다시 보여준다. 실제 재계약 문서 자동 생성은 P1이다.

### 6.13 최소 분석 대시보드

표시 항목:

- 전체·서명 중·진행·완료 계약 수
- 만료 임박 계약 수
- 미해결 확인 신호 수
- 조정 요청·합의·거절 조항 수
- 이행 대기·제출·확인 완료 건수
- 총 약정액과 지급 조건 충족 금액
- 가장 자주 발견된 확인 유형

분석하지 않는 항목:

- 광고 성과의 자체 측정과 매출 기여도
- 업체 사기 가능성
- 업체 전체 신뢰점수
- 계약의 위법성

### 6.14 광고효과 기록과 대조

대행사가 매월 제공하는 광고 리포트를 소상공인이 업로드하면, 지표를 구조화해 보관하고 계약에서 약속한 조건과 대조한다.

제품은 광고 성과를 측정하지 않는다. 대행사가 보고한 값을 소상공인이 확인해 기록하고, 계약 조항과 다른 부분을 표시할 뿐이다.

대행사를 이 흐름에 참여시키지 않는다. 대행사는 계약 단계에서 토큰 링크로만 접근하며, 리포트는 기존에 쓰던 방식(메일·메신저) 그대로 전달한다. 대행사에 새로운 입력 부담을 만들지 않는 것이 이 설계의 전제다.

흐름:

`리포트 업로드 → 지표 추출 → 소상공인 확인·수정 → 대시보드 집계 → 계약 조건 대조 → 문의 문안 생성`

지표 범위:

| 구분 | 항목 | 근거 |
| --- | --- | --- |
| 필수 | 노출(조회) 수, 좋아요, 댓글 | 플랫폼 인사이트의 기본 값이라 대행사 부담이 낮다 |
| 선택 | 도달, 저장, 공유, 팔로워 순증 | 리포트에 있으면 기록하고 없으면 비운다 |
| 계약 대조 | 실제 게시물 수 | 리포트에 명시되었거나 소상공인이 확인한 경우에만 기록한다 |
| 자동 계산 | 반응률 = (좋아요+댓글+저장+공유) ÷ 노출 | 입력값에서 파생하며 별도 입력을 요구하지 않는다 |
| 소상공인 입력 | 문의·예약·구매 수 | 대행사가 알기 어려운 값이라 선택 입력으로만 둔다 |

전환율·CPA·ROAS는 요구하지 않는다. 대행사의 추가 분석 노동을 유발하고, 리포트 등급에 따라 별도 비용이 발생하는 항목이기 때문이다.

추출과 확인:

- Upstage Document Parse로 PDF·이미지 리포트의 구조를 보존해 읽는다.
- Solar가 지표명과 숫자를 매핑해 항목별 확신도와 함께 반환한다.
- 추출값은 AI 초안으로 분리해 저장한다. 소상공인이 확인·수정한 확정값만 대시보드,
  계약 대조와 재계약 검토에 사용한다.
- 원본 파일은 같은 계약의 private `Document`로 보관하고
  `Document.type=PERFORMANCE_REPORT`와 `source_document_id`로 연결한다.
- 계약과 `period(YYYY-MM)`별 논리 리포트는 한 건만 저장한다. 여러 채널은 P2에서
  나누지 않으며 같은 달의 두 번째 리포트 대신 기존 리포트의 정정 이력을 남긴다.
- 추출 작업은 원자적으로 점유하고 시작 시각과 attempt ID를 기록한다. 15분 이상 멈춘
  작업만 새 멱등 키를 사용한 소상공인의 명시적 재시도로 복구하며, 오래된 작업의 늦은
  응답이 새 결과를 덮어쓰지 못하게 한다. 서버가 자동으로 외부 AI 호출을 재개하지 않는다.

계약 조건 대조:

계약 분석에서 추출한 산출물 약정(예: 월 4건 게시)과 소상공인이 확정한 지표를 비교해
확인이 필요한 지점을 표시한다.

- 계약 원문의 월 수량과 월 단위가 모두 검증되고 실제 게시물 수가 약정보다 적은 경우
- 달력상 바로 전월과 현재 월의 `saves`·`shares` 포함 구성이 같고 양쪽 노출 수가
  1,000 이상일 때,
  반올림 전 반응률이 절대 1.0%p 이상이면서 상대 25% 이상 낮아진 경우

실제 게시물 수가 약정과 같거나 많거나, 첫 달·전월 누락·0 노출·표본 미달·
`saves`·`shares` 포함 구성 차이가 있으면 해당 자동 신호를 만들지 않는다. 반응률은
원본 정수에서 `Decimal`로
결정 계산하며 표시용 반올림값을 판정에 다시 사용하지 않는다.

표시는 판정이 아니라 확인 신호이며, 조항 카드와 동일한 톤 규칙을 따른다.

문의와 기록:

- 확인이 필요한 지점에 대해 대행사에 보낼 문의 문안을 version이 고정된 결정적 템플릿으로
  확정·정정 시 생성한다. 근거 조항을 함께 인용하고 revision별 snapshot으로 보존한다.
- 문안은 제품이 발송하지 않는다. 소상공인이 복사해 기존 채널로 직접 보낸다.
- `이상 있음` 기록은 사유와 날짜를 남기고, 재계약 검토 시 근거로 다시 보여준다.
- 확정 뒤 오기를 고칠 때는 과거 값·신호·문안을 덮어쓰지 않는다. 가장 최근에 확정된 월에만
  직전 version과 정정 사유가 연결된 새 revision을 추가하고 최신 revision만 집계에 사용한다.

구현하지 않는 것:

- 광고 성과의 자체 측정과 매출 기여도 분석
- 플랫폼 API 직접 연동을 통한 지표 자동 수집
- 대행사 성과의 우열 평가와 점수화
- 리포트 위·변조 판정

## 7. AI 설계

### 7.1 모델별 역할

| 구성요소 | 역할 |
| --- | --- |
| Upstage Document Parse | PDF 구조·문단·표·페이지 보존 |
| Information Extract | 핵심 계약 필드 JSON 구조화 |
| Solar LLM | 쉬운 설명, 불일치 해석, 보완 문구, 역제안 비교 |
| 일반 코드 | 날짜·총액·비율 계산, 스키마 검증, 상태 전환 |

### 7.2 구현할 Agentic Loop

하나의 Evaluator Loop만 실제 구현한다.

1. 계약서와 1차 추출 결과 관찰
2. 필수 필드 누락·모순·근거 부족 확인
3. 필요한 필드만 재추출
4. JSON 스키마와 원문 근거 검증
5. 미해결이면 한 번 더 시도
6. 최대 2회 후 `확인 필요`로 종료

자동으로 하지 않는 행동:

- 요청서 발송
- 계약 문구 확정
- 상대방 응답 수락
- 모두싸인 서명 요청
- 이행 승인
- 재계약·종료 선택

### 7.3 신뢰성 장치

- 모든 추출·경고에 원문 페이지와 문장 표시
- 원문이 없는 결과는 사용자에게 확정값으로 표시하지 않음
- 생성 결과와 검증 결과가 다르면 `확인 필요`
- 날짜·금액 계산은 코드로 재검산
- AI 원문·사용자 입력·제안 문구를 시각적으로 구분
- 발송·합의·서명·승인은 항상 사람 확인
- 프롬프트 버전과 모델 응답 로그 저장

### 7.4 평가 데이터

고정 샘플 계약 10건을 준비한다.

- 기간·총액 불일치
- 환불 설명 누락
- 자동갱신
- 모호한 산출물
- 빈칸 다수
- 위약금 조건
- 촬영 안전·손해 책임
- 콘텐츠 권리
- 정상 계약
- OCR 품질이 낮은 계약

목표 지표:

- 핵심 필드 추출 정확도 90% 이상
- 근거 페이지 연결 정확도 90% 이상
- 필수 JSON 스키마 성공률 100%
- 기간·총액 불일치 탐지율 100%
- 근거 없는 확정 경고 0건

수치는 제출 전 실제 평가 결과로 교체하며 달성하지 못한 값은 그대로 공개한다.

## 9. 기술 구조

### 권장 스택

- 프론트엔드: Next.js, TypeScript, Tailwind CSS
- 백엔드: FastAPI, Pydantic
- DB·파일: Supabase PostgreSQL·Storage
- 문서·AI: Upstage Document Parse, Information Extract, Solar
- 전자서명: 모두싸인 API·Webhook
- 배포: Vercel + 관리형 Python 배포 환경

### 구조

```
사용자 브라우저
    ↓
Next.js 웹
    ↓
FastAPI
    ├─ Upstage Adapter
    ├─ Solar Review Service
    ├─ Modusign Adapter
    └─ Supabase DB·Storage
```

외부 API는 Adapter 뒤에 두어 실제 API와 Mock을 환경변수로 전환한다. Mock 결과를 실제 연동이라고 발표하지 않는다.

### 보안 최소 기준

- 모든 외부 API 키는 서버 환경변수에만 저장
- 공개 조정 링크는 추측하기 어려운 토큰과 만료시간 사용
- 공개 링크에서 상대방에게 불필요한 개인정보를 표시하지 않음

## 11. 상태 머신

### 계약

`DRAFT → ANALYZING → REVIEW_REQUIRED → NEGOTIATING → READY_TO_SIGN → SIGNING → SIGNED → IN_PROGRESS → COMPLETED / RENEWAL_DUE`

### 조정 요청

`DRAFT → SENT → OPENED → RESPONDED → CONFIRMED / EXPIRED`

### 모두싸인

외부 상태:

`ON_PROCESSING → ON_GOING → COMPLETED / ABORTED / PROCESSING_FAILED`

모두싸인의 `DRAFT`, `SCHEDULED` 상태도 저장할 수 있게 하되 MVP 정상 흐름에는 사용하지 않는다. 외부 상태와 내부 계약 상태·사용자 표시 문구는 Adapter에서 매핑한다.

### 광고효과 리포트

`UPLOADED → EXTRACTED → CONFIRMED / FLAGGED`

`CONFIRMED`·`FLAGGED`는 기존 revision을 변경할 수 없다는 의미에서 terminal이다.
정정은 terminal 값을 덮어쓰지 않고 가장 최근 확정 월에 새 immutable revision을 추가한다.
report의 현재 projection은 최신 revision에 따라 `CONFIRMED`와 `FLAGGED` 사이에서 바뀔 수
있지만 과거 revision·신호·문의 문안 snapshot은 변하지 않는다.

추출 중에는 attempt ID와 시작 시각으로 작업을 점유한다. 15분 미만의 활성 작업은 중복
실행하지 않고, 15분 이상 멈춘 attempt만 새 멱등 키의 명시적 재시도로 복구한다. 현재
attempt와 다른 늦은 결과는 저장하지 않는다.

### 이행 항목

`PENDING → APPROVED / DISPUTED` 또는 `PENDING → SUBMITTED → APPROVED / DISPUTED`

`APPROVED`일 때만 서비스 화면에 `지급 조건 충족`을 표시한다. 이는 실제 지급 승인이나 법적 채무 이행 판정이 아니다.

## 17. 예상 질문과 답변

### 법률 자문 서비스인가?

아니다. 법적 유효성이나 위법성을 판정하지 않고 계약 원문·사용자 이해조건·공식 기준 사이의 차이를 보여준다. 최종 결정과 발송·서명은 사람이 한다.

### 사용자가 잘못 기억한 설명이면 어떻게 하나?

사용자 답변을 객관적 증거로 표시하지 않고 `사용자가 이해한 내용`으로 구분한다. 메시지·제안서 등 기록이 있을 때만 문서로 확인된 설명으로 표시한다.

### 별도 합의서와 원계약이 충돌하면?

원계약을 식별하고 변경 전·후 조항을 명시한 변경·확인 합의서를 사용한다. 실제 서비스 출시 전 문서 우선순위 표현은 법률 전문가 검토가 필요하다.

### 왜 실제 송금은 하지 않나?

송금은 금융 API·본인인증·오지급 책임이 추가된다. MVP는 계약상 산출물의 증빙과 사용자 확인을 거쳐 `지급 조건 충족`을 표시하는 데까지 자동화한다.

### 관리 단계가 너무 얕지 않나?

범용 프로젝트 관리가 아니라 계약서의 산출물 한 건을 실제 업무와 증빙으로 전환하는 수직 흐름을 구현한다. 이후 여러 산출물·지급·외부 플랫폼 검증으로 확장한다.

### 왜 부산 관광상권인가?

SNS·촬영·외국어 콘텐츠 계약이 빈번하고, 계약 검토 인력이 부족한 관광상권을 초기 실증시장으로 선택했다. 제품 구조는 다른 지역 소상공인으로 확장할 수 있다.

### AI 신뢰성을 어떻게 증명하나?

모든 결과에 원문 페이지·문장을 연결하고, 계산은 코드가 수행하며, 추출 후 별도 검증 단계를 거친다. 고정 계약 10건의 정확도와 실패 결과를 함께 공개한다.

## 20. 최종 확정 사항

- 제품: 부산 관광상권 소상공인용 AI 광고대행 계약 CLM
- 형태: 모바일 우선 반응형 웹
- 소상공인 인증: 이메일·비밀번호 회원가입·로그인, 이메일 확인·재설정, Supabase Auth 소유자 세션
- 대표 계약: SNS·블로그 광고대행 + 매장 촬영
- 비교 기준: 사용자가 이해한 조건 5문항 + 선택 자료
- 핵심 문제: 기간·총액·해지·환불·산출물
- 협상 방식: 조항 단위 비동기 요청, 상대방 무가입 링크
- 협상 범위: 1회 수락·거절·역제안
- 서명 문서: 광고대행 계약조건 변경·확인 합의서
- 전자서명: 모두싸인 실제 API·웹훅
- Agentic Loop: 계약 검토 Evaluator Loop 하나
- 관리: 산출물 1건의 증빙 제출·확인 + 월별 광고효과 기록·계약 조건 대조 + 계약 일정
- 분석: 계약·위험·조율·이행·만료 최소 대시보드
- 다국어: 일주일 MVP에서 제외
- 송금·광고 성과 자체 측정·매출 기여도 분석·사기 판정: 제외
