# Solar 검토 문구 live 연동 결과

2026-07-31에 고정 가상 계약 3건으로 Upstage Solar Chat API를 실제 호출했다.
실제 사업자 정보나 계약서는 사용하지 않았으며, 아래 내용은 원시 HTTP 응답이 아니라
Adapter의 보안 검사와 Pydantic 스키마를 통과한 필드만 기록한 결과다.

## 실행 결과

| 항목 | 결과 |
| --- | --- |
| 완료 시각 | 2026-07-31 09:05:34 UTC (18:05:34 KST) |
| endpoint | `POST /v1/chat/completions` |
| 요청 모델 | `solar-pro3` |
| 프롬프트 버전 | `contract-review-copy-v1` |
| 실제 요청 수 | 3회, 요청당 가상 검토 항목 1건 |
| 응답 스키마 | 3/3 통과 |
| 쉬운 설명 | 3/3 생성 |
| 원안 수용·절충·요청 문구 | 3/3 모두 생성, 항목별 세 문구 상호 구분 |

## 검증된 생성 문구

### 기간·총액 불일치

- 쉬운 설명: 계약서 원문의 총 계약금액과 사용자가 이해한 금액이 서로 달라 정확한
  금액을 확인해야 합니다.
- 원안 수용: 원문에 명시된 총 계약금액 3,600,000원을 그대로 수용합니다.
- 절충: 원문의 3,600,000원과 사용자의 6,000,000원 중 실제 계약 금액을 협의해
  조정합니다.
- 요청: 누락된 금액 산정 기준이나 추가 비용 항목을 구체적으로 요청합니다.
- 모델 한계: 제공된 정보만으로 금액 차이의 원인을 판단할 수 없어 계약서 전체와
  당사자 확인이 필요합니다.

### 모호한 산출물

- 쉬운 설명: 산출물 수량에 '별도 협의'라는 표현이 있어 실제 제공될 콘텐츠 양을
  미리 알기 어렵습니다.
- 원안 수용: 산출물 수량은 별도 협의에 따라 결정한다는 현재 문구를 수용합니다.
- 절충: 사전에 합의한 최소·최대 범위 안에서 별도 협의하도록 구체화합니다.
- 요청: 최소 수량·단가·산정 방식 등 구체적인 기준을 명시하도록 요청합니다.
- 모델 한계: 입력된 계약 텍스트만으로 실제 적용 방식을 판단할 근거가 부족해 계약
  당사자와 전문가의 확인이 필요합니다.

### 촬영 안전·손해 책임

- 쉬운 설명: 촬영 안전 조항의 '모든 책임'이 누구에게 어떤 상황에서 적용되는지
  명확히 확인해야 합니다.
- 원안 수용: 촬영 안전 책임을 광고주가 전부 부담한다는 현재 조항을 수용합니다.
- 절충: 광고주가 기본 책임을 부담하되 특정 위험 상황은 양측이 협의해 분담합니다.
- 요청: 사전 점검·비상 대응 등 책임의 구체적인 범위와 주체를 명시하도록 요청합니다.
- 모델 한계: 제공된 문구만으로 책임 범위와 적용 상황을 완전히 판단하기 어려워 계약
  전체와 관련 법령을 사람이 검토해야 합니다.

## 실패·재시도 기록

- 같은 3건을 한 요청에 담은 최초 live 배치는 설정된 120초 timeout 후 전송 오류
  재시도를 한 번 수행했지만, 두 번째 시도도 `ReadTimeout`으로 끝났다.
- 입력을 한 건씩 분리한 후 실제 요청 3회가 모두 성공했다. 따라서 endpoint·인증·
  strict JSON Schema 연동은 성공했지만, 3건 비스트리밍 배치는 현재 timeout 안에서
  안정적이라고 볼 수 없다.
- 후속 구현에서 production 분석과 이 live 평가 실행기는 모두
  `SolarReviewAdapter.generate_review_content`의 기본 1건 chunk 전략을 사용하도록
  통일했다. 전체 입력 ID·순서 검증이 끝나기 전에는 어떤 chunk 결과도 분석에 저장하지
  않는다.
- 이 변경 후 2026-07-31 09:05:34 UTC에 production과 같은 1건 chunk 전략으로
  외부 호출 3회를 다시 실행했고 모두 성공했다. 첫 샌드박스 격리 실행은 외부 연결이
  차단되어 HTTP status 없는 `ConnectError`로 종료됐으며, 네트워크 허용 환경에서
  동일 명령을 재실행해 위 결과를 얻었다.
- 자동 테스트는 `429` 응답 뒤 한 번 재시도하여 성공하는 경우, 전송 timeout을 한 번
  재시도한 뒤 `SolarReviewError`로 종료하는 경우, 잘못된 JSON과 스키마·ID·안전·
  입력 근거 검증 실패, 뒤 chunk 실패 시 부분 결과를 반환하지 않는 경우를 검증한다.

## 재현 방법

실제 외부 호출과 비용이 발생한다. `apps/api/.env`에 `UPSTAGE_API_KEY`를 설정한 뒤
명시적인 확인 옵션으로 실행한다.

```bash
cd apps/api
.venv/bin/python -m evaluation.solar_live --confirm-live
.venv/bin/python -m pytest \
  tests/test_solar_adapter.py \
  tests/test_solar_live_evaluation.py -q
```

일반 `pytest`는 외부 Solar를 호출하지 않는다. live 결과는 모델 변경, 프롬프트 변경,
timeout 정책 변경 전후에 별도로 다시 실행해 기록한다.
